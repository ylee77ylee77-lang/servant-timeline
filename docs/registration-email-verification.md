# Registration email verification rollout

This branch only changes self-service registration and the server-side contact-email verification boundary. Existing internal Supabase Auth emails and password login are unchanged. Existing administrator-created/legacy accounts remain on the prior reviewed recovery procedure. New self-registered users require a verified recovery address; changing it clears verification and prevents sending recovery credentials until it is verified again. Personal-settings verification of legacy/changed addresses is a follow-up, not part of this registration release.

Before merging:
- Apply the CLI-generated versioned migration `20261126040922_registration_email_verification.sql` to an isolated database first. Never apply to production as part of a build.
- Test migration and SQL authorization on an isolated Supabase database, including lint/build/Node tests. The CI-only registration integration starts Next.js against the disposable database, exercises real API routes and registration claims with seeded challenges, and verifies SMTP failure without sending email. Review security advisors.
- Configure a randomly generated, at least 32-byte server-only secret in `REGISTRATION_VERIFICATION_SECRET` for each target environment. Do not use `NEXT_PUBLIC_` or commit any value. Keep the existing Gmail SMTP settings. Use an isolated Supabase project and sender/recipient for preview email tests; do not create test accounts in production.
- Preview email link in Gmail and Apple Mail on iPhone and Android; test browser continuation, six-digit long-press copy/paste without opening a browser, leading zero, wrong/expired codes, 60-second resend, 5-attempt lock, changing email, scanner/link rewriting, duplicate submits, pending administrator approval, and old login/account recovery.
- Public email-send limits are 30 attempts per rolling day globally, 5 per hour per address, 60 seconds between sends to one address/session, and 15 per ten minutes per trusted client source. Failed sends count toward quota. Review limits before a large volunteer registration event.

Link tokens use a URL fragment and are consumed by a same-origin POST, avoiding normal GET-only scanners. A scanner executing browser JavaScript or an email client rewriting fragments may still interfere; the visible six-digit code and resend path are fallbacks. Link redemption transfers the registration capability to the redeeming browser. The initiating PWA retains status-only visibility; returning to the foreground refreshes its status. If the user wants to resume there, the original six-digit code can authorize a one-time transfer within its original 10-minute lifetime. Failed handoff attempts count toward the original five-attempt limit without invalidating the verified browser. Both surfaces can display verification, but only the current credential can claim registration. A consumed claim is shown as used, not asserted to be a successfully created account. Links redeemed before this migration cannot have their original session reconstructed. No password is saved before verification. Registration completion is a separate, atomic single-use claim and continues through the existing administrator approval workflow.

Do not merge or deploy until both database and application checks, preview configuration, and real-device mail tests pass.

## Transactional mail delivery

Registration verification messages use one direct first-party verification link in HTML and plaintext, with an uninterrupted, selectable six-digit code and no copy-link, external images, tracking or marketing content. Old copy URLs remain supported for previously delivered emails; no new copy URLs are sent. Keep the same authenticated Gmail SMTP mailbox, and use the fixed registration sender display name 夏凱納招待服事. Account recovery sender settings are unchanged. Two delivered samples inspected on 2026-11-26 passed SPF, DKIM and DMARC; this does not prove delivery to every recipient or diagnose every spam placement. For further diagnosis, inspect only authentication outcomes in the affected message's original headers; avoid sharing verification tokens, codes, or private addresses. No DNS or sending-service changes are needed on current evidence.
